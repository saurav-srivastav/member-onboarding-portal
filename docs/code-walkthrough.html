Interview prep · code round

Portal Code Walkthrough

What the member-onboarding portal is made of, where every knob lives, and how to change one while someone watches.

Repo: member-onboarding-portal Stack: Flask · SQLite · Jinja ~1,500 lines Python, 1,600 templates

1The sixty-second answer

If he opens with “walk me through it”, this is the whole thing — say it in this order and stop:

Four Python files and a templates folder. app.py is routes only — HTTP in, HTML out, no business logic. models.py holds the schema, the state machine and the metrics; every database write goes through it. documents.py is pure configuration — the checklist and the form, no logic at all. seed.py builds the demo data. The rule I kept was that routes never touch SQL and never change a stage directly — they call a named function in models.py, so the state machine has exactly one door.

That last sentence is the one that matters. It is a structural claim he can test, and it is true.

2The map

app.py 491 lines · routes, one section per persona models.py 477 lines · schema, state machine, metrics — all SQL lives here documents.py 130 lines · the checklist + form definition. Config, no logic seed.py 232 lines · demo applications, dates relative to today test_app.py 222 lines · one member, invitation → live, 41 checks templates/ base.html the design system + role switcher — every page extends it _macros.html stage strip, timeline, status pills — shared components member_*.html form → documents → review → status → live ops_*.html queue + application detail compliance_* queue + review/decision tech_* provisioning queue + checklist pipeline.html Service Management — all applications, metrics

Five tables, and the shape of them is the design: applications (one row per application, current stage on it), stage_history (append-only, one row per transition), documents (per application × document, with a returns counter), clarifications (the Ops-routed queries, carrying the TO_ROUTE state), and provisioning_tasks. Schema is models.py:52 — one executescript, readable in a minute.

3The two decisions worth leading with

Metrics are derived, never stored

Every stage change writes a timestamped row into stage_history (models.set_stage, line 149). Time-to-onboard, time-in-stage, first-time-right and round-trips are all computed from that history in models.metrics (line 455). There is no duration column anywhere.

Why it matters, in his language: a stored duration drifts the moment anyone corrects a record by hand. Deriving it means the number cannot disagree with what actually happened — and the audit trail and the metric are the same object, so you get the operations-reporting view for free.

This is also the JD's “north-star metric made observable” expressed in a schema rather than a slide. If he asks how you would prove the portal moved the metric, the answer is that the portal is the instrument.

The Operations-only channel is enforced in state, not in the UI

A KYC-vendor or Compliance query is created with status TO_ROUTE. The member's view queries only OPEN items. It becomes OPEN exclusively through models.route_to_member (line 413), which Ops triggers.

The point: hiding it in the template would be a UI convention that the next developer breaks by accident. Making it a state the member's query cannot reach makes the rule structural. test_app.py asserts the member's page does not contain the query text before routing, and does after.

The return loop is per-document

models.return_doc (line 371) moves one document to RETURNED, raises a clarification carrying the reason, and sends the application back to DOCUMENTS. Everything else keeps its status. When the member re-uploads, maybe_return_to_ops (line 342) puts it back in the Ops queue without a fresh submission. That is the email round-trip collapsed into one document.

5Three live-change drills

Practise these once each so your hands know them. Debug mode is on, so the server reloads on save — no restart needed.

Tighten the Ops review SLA from 3 days to 2

models.py:34, change "OPS_REVIEW": 3 to 2, save, refresh /ops. On freshly seeded data, Straits Derivatives picks up an amber flag it did not have, and the tile's “approaching” count goes from 1 to 2. Say why it is visible immediately: the flag is computed per request from the stage-entry timestamp — sla_state, line 232 — and is not stored on the row, so changing the threshold reclassifies history as well as new work.

Add a tenth required document

Append to DOCUMENTS in documents.py:

{
    "id": "business-continuity-plan",
    "name": "Business Continuity Plan",
    "description": "Your BCP covering trading and settlement operations.",
    "formats": ["pdf", "docx"],
},

Refresh the member's document page — it appears with the right formats and validation, on applications that already existed, and Meridian's outstanding count goes from 1 to 2.

This drill is worth telling as a story, because it found a real bug. The first version of app_docs assumed every configured document had a database row, so adding one to the checklist raised a KeyError on every application created before the change — the config edit looked harmless and took the whole portal down. The fix (models.py:170) backfills missing rows on read, and there is now a test for it. Two useful things to say: I only found it because I tried the change rather than reasoning about it; and the deeper answer is that a production system would version the checklist and snapshot the required list onto each application at creation, so changing today's requirements does not retroactively alter an application decided last year — which matters for an audit trail.

Make the member's phone number mandatory

models.py:207, in form_missing, remove the fid != "contact_phone" exclusion. Submission is now blocked until it is filled, and the form-progress panel shows the gap. One line, two screens change — that is the separation working.

6Running it

Re-seed before any demo. The seed dates are relative to the day you run it, so the story drifts: Pacific Rim reads 9 days over SLA on seed day and 11 today. One command puts it back.

cd ~/Documents/projects/member-onboarding-portal
./.venv/bin/python seed.py        # reset demo data (destructive)
./.venv/bin/python app.py         # start — http://localhost:5001
./.venv/bin/python test_app.py    # 41 checks, invitation → live

Stop with Ctrl+C; if the port is stuck, lsof -ti:5001 | xargs kill.

The single most persuasive thing to show, if there is a screen: on the Ops detail page for Nikko Futures, click Route to member, then switch to the Member role. The vendor's question is now in their clarifications and was not there thirty seconds earlier. That demonstrates the state rule rather than describing it.

7Where it breaks — say these before he finds them

He tests delivery realism. Volunteering the limits is worth more than defending the build.

  • SQLite and concurrency. Fine for one Ops user and low volume; two people accepting documents on the same application at once is a write-lock waiting to happen. Postgres is the swap, and because all SQL is in one module it is a contained change.
  • No authentication. The role switcher is a stand-in. Every route trusts the URL — /ops/MEM-2026-037 is reachable by anyone. Deliberate for a prototype, unshippable without SSO and per-role authorisation.
  • Uploads are unscanned. Extension and size are validated, content is not. Real onboarding needs malware scanning and probably content checks before anything reaches a reviewer.
  • One application per member. No concept of a firm applying for a second membership class, which a real exchange needs.
  • Metrics recompute on every page load. Fine at nine applications, wrong at nine thousand — it walks every application's documents. Cache or aggregate when it matters, not before.
  • No notifications. The PRD specifies email on stage change; the portal holds the state they would link to, but nothing sends.
  • Hardcoded secret key (app.py:25), labelled prototype-only. Correct for a demo with no sessions to protect, and the first thing to move to an environment variable.

8Questions he is likely to ask

You built this with Claude Code. What did you decide?

The ones that shaped the data model, and you can point at each: Operations as the single channel — which is why clarifications have a TO_ROUTE state at all; per-stage SLAs rather than one global threshold, because the stages differ by an order of magnitude in expected duration; the application form filled in-portal rather than uploaded, which is what makes field-level validation possible; and sequencing the KYC vendor API second, which is why Ops records dispatches and results manually today.

Then the honest half: the AI wrote the code fast, and the review is where the work was. Three examples you can name — the internal screens could originally see the document pack but not the submitted form answers, which is a real hole once the form stops being a PDF; the first-time-right metric read 100% because the seed data never recorded the returns that had actually happened, so the number was flattering and wrong; and adding a document to the checklist crashed every existing application, which I only found by making the change instead of reasoning about it.

That last one is the most useful thing to say about working this way. Generated code compiles and runs, which is exactly what makes it dangerous — a clean start-up tells you nothing about whether it is right. What earns the speed is checking output against a case you already know the answer to.

How would you hand this to an engineering team?

As the specification, not the implementation. The PRD gives the stages and the rules, the schema gives the data model, and test_app.py is executable acceptance criteria — forty-one checks that state what the system must do, in the order a member experiences it. A team can rewrite every line in their own stack and keep those assertions as the contract.

What happens if the vendor never comes back?

Today: it sits in KYC, the per-stage SLA flags it amber then red on the Ops queue and the pipeline, and it is visibly stalled. What it does not do is escalate to anyone — the PRD specifies reminder notifications and they are not built. That is the honest answer, and the fix is a scheduled job reading the same stage_history the flags already use.

Why SQLite? / Why Flask?

Because the point was to make the flow decidable, not to pick a production stack. SQLite means no infrastructure between an idea and a working screen, and Flask means the routes read like the process. Both are swaps a team makes on day one — and neither choice leaks into the design, because the schema and the state machine are the parts worth keeping.

Show me where you would add a rule — say, financials must be under 18 months old.

That is not a format check, so it does not belong in the upload path. It is a review criterion: a field on the document entry in documents.py for the reviewer prompt, surfaced in the Ops accept/return panel as a checklist item, with the return-reason template already there. If it later needs to be automatic, it becomes a document-metadata question — you would have to capture the statement date at upload, which is a form field, not a file property.

9Two rules for the room

Do not assert how the exchange works internally. He ran digital and depository services there for seven years. Frame every domain claim as a design assumption you made and would test — “I assumed Operations owns the vendor relationship; if that sits elsewhere the routing changes but the state machine does not.” Assumptions invite correction; assertions invite contradiction.
Own the AI use plainly. He knows. The credible position is not that you wrote it by hand — it is that you can navigate it, change it, and name what is wrong with it. This document is that claim: the map, the knobs, the limits. If you can do the third drill in front of him and say what it breaks, the question is answered.
One page, one screen, one honest limit — that is the whole preparation. If you have ten minutes before the call, re-run seed.py, do the SLA drill once, and re-read section 7.
